## 3. What Went Well

### 3.1 5-1 使命宣言完整交付

5-1 是 Epic 5 中最干净的 story — 9 个 Task 全部完成，16 个 Rust 测试 + 7 个前端 service 测试 + 24 个回归测试全部通过，Review Findings 5 个 Patch 全部修复。使命宣言从 mock 状态到真实持久化，柯维四段式结构化模板从三段式重构为四段式（使命→原则→角色与目标），执行扎实。

### 3.2 5-2 LLM 推断服务设计合理

5-2 的 LLM 推断服务采用双 Pool 访问（主 DB + 对话 DB），数据不足时优雅降级返回 None，推断结果不持久化避免过期数据。`build_default_provider` 和 `call_llm_with_timeout` 采用方案 A（复制实现），保持了模块独立性。

### 3.3 `protection_status` 枚举化终于完成

从 Epic 3 开始连续四个 Epic 提出后终于落地。`ProtectionStatus` 枚举 + `as_str()` + `FromStr` + `Display` 实现完整，DB 层和 service 层都已使用枚举方法替代裸字符串。

### 3.4 范围裁剪决策正确

Epic 5 将 4/6 stories 延期到 V2 是正确的产品决策。使命宣言和行为推断是冲突仲裁的基础设施，先完成这两个为 V2 仲裁链路奠定了基础。

## 4. Challenges and Friction

### 4.1 5-3 状态不一致（严重）

Story 5-3 存在严重的状态不一致 — story 文件标记 `done`，Review Findings 有 7 项实际审查记录，但 sprint-status 标记 `deferred-v2`，代码库中只有迁移文件 `021_conflicts.sql`，Rust 实现代码完全不存在。这意味着代码曾被编写和审查，但最终未合并或被移除，story 文件状态未同步更新。回顾时已修复 story 文件状态。

### 4.2 Dev Agent Record 完整性仍未稳定

Epic 4 复盘建立了行动项要求 story 标记 done 前必须填写 Completion Notes + File List。5-1 执行了，但 5-2 没有执行 — Completion Notes 和 File List 全部为空。这个行动项已经连续两个 Epic 未稳定执行。

### 4.3 LLM 调用代码重复

5-2 采用方案 A 复制了 `task_classifier.rs` 中的 `build_default_provider` 和 `call_llm_with_timeout`（约 60 行）。如果 Epic 6 再复制一次，就有三份相同代码。需要在 Epic 6 前将 LLM 调用工具提取为公共模块。

### 4.4 5-3 迁移文件孤立

迁移文件 `021_conflicts.sql` 已存在于代码库中，但对应的 Rust 实现代码不存在。V2 恢复 5-3 时需要确认迁移是否已在开发数据库中执行，以及是否需要处理空表。

## 5. Key Learnings

1. **Story 延期时的状态同步** — 5-3 暴露了流程缺口：story 被延期时，story 文件的状态标记未同步更新。需要建立"延期时同步 story 文件状态"的规则。
2. **Dev Agent Record 行动项执行不稳定** — 连续两个 Epic 建立了文档完整性要求，但仍有 story 未执行。说明行动项的执行依赖于开发者自觉，缺乏强制检查机制。
3. **范围裁剪决策正确** — 使命宣言和行为推断先完成，为 V2 仲裁链路奠定基础。
4. **`protection_status` 枚举化终于完成** — 跨四个 Epic 的债务清偿，说明持续追踪有效但效率偏低。
