## 手机伴侣（Android）— 技术注记（2026-08-25，随 §4.14 决策产生）

### 关系模型（产品边界的技术表达）

- **单一事实源**：桌面端持有 egosync.db / conversations.db / keyring / opencode sidecar；手机端无本地业务库主权，只维护「最后已知快照缓存」。
- **四通道协同**：
  1. 连接通道：局域网自动发现直连 → 出网经云中继加密转发
  2. 状态通道：桌面状态变化主动推送至手机（长连接），对应 FR-41
  3. 指令通道：手机操作 = 远程命令，桌面引擎执行后结果回流
  4. 推送通道：三级通知 → Android 系统通知渠道，对应 FR-42
- **诚实代价**：桌面关机 = 手机降级为只读快照 + 速记排队（FR-43）。这是本地优先架构的固有属性，不是缺陷。

### 已否决备选（记录理由，防止回头重提）

| 备选 | 否决理由 |
|------|----------|
| B. 独立手机 App + 云端托管引擎 | 违背本地优先愿景；需第二套引擎；双数据源冲突是工程深坑 |
| C. 仅响应式 Web (PWA) | iOS 推送受限（本次仅 Android 影响减小）、出网需隧道、体验打折；但可作为后续低成本验证手段 |

### 留给架构阶段的开放点

- **App 技术栈**：Kotlin 原生 vs 跨端复用现有 React 组件（Capacitor/Tauri Mobile）— 需评估流式渲染、后台推送、与现有前端代码复用率的权衡
- **中继方案**：自建 WebSocket 中继 vs 成熟隧道方案（如 Tailscale 类）；关键约束 = 端到端加密、零落地存储、成本可控 `[PRD ASSUMPTION]`
- **配对与信任**：扫码配对的密钥交换机制（mTLS / token 配对），重装恢复流程
- **推送链路**：FCM 与自建通知的分界；桌面未运行时无新通知是既定行为（FR-42）
- **快照口径**：FR-41/43 的「最后已知快照」包含哪些域（角色活动/任务/仪表盘指标）、缓存大小上限

### 明确不做（与 PRD Non-Goals 对齐）

- 手机本地 AI 引擎；iOS 伴侣 App（V2）；云端数据同步/托管（V2）
