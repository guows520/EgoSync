## 3. What Went Well

### 3.1 后台 LLM 调用范本成功复用

4-2 完整复用了 `memory_pipeline.rs` 的 `chat_stream + mpsc + timeout + 大小上限` 模式，零额外依赖实现建议生成。这个范本从 Story 2.6 建立以来已被多次验证。

### 3.2 调度器从硬编码到 DB 驱动的演进

4-1 实现过程中主动将调度器从硬编码 interval 改为 DB 驱动的 HH:MM 时间点，并新增前端配置 UI。这是正确的架构决策 — 用户可自定义触发时间，比原 epic 设计更灵活。

### 3.3 LLM 判重替代余弦相似度

4-2 识别到原 epic 写的"余弦相似度 > 0.85"在代码库无向量基础设施，果断改为 LLM 判重 + 确定性兜底。避免了引入 embedding 依赖，控制了 story 范围。

### 3.4 4-3 极简实现一次通过

4-3 只修改 2 个文件、新增 10 个单测，实现一次通过、零调试。这是 Epic 4 中最干净的 story — 纯函数 + 精确接入点 = 最少出错面。

### 3.5 4-7 批量查询优化

4-7 将"逐角色查询任务统计"优化为单条 `GROUP BY` 批量查询，减少 DB 往返。仪表盘数据接通干净，Dev Notes 决策记录清晰。

### 3.6 4-8 首次计算保护

4-8 第二轮 review 发现新建角色首次能量计算会从 100 跌至 30 并误发"能量偏低"通知，修复为首次计算只建立基线、跳过通知。这是对用户体验的细致关注。

## 4. Challenges and Friction

### 4.1 4-8 提交代码编译失败（严重）

4-8 第一轮 review 发现 **提交代码从未编译通过** — `ConversationsPool` 不满足 `Executor` trait，6 个 E0277 编译错误。测试夹具还有列/值错位 + 占位符数量不匹配。这意味着 `cargo test` 在 story "done" 前从未成功运行。

**根因**：Dev Agent Record 为空、Completion Notes 为空 — 实现后未执行验证命令就标记了完成。

### 4.2 Review Patch 密度显著上升

| Epic | Stories | Review Patches | 平均/story |

| Epic 3 | 7 | ~8 | 1.1 |
| Epic 4 | 8 | 25+ | 3.1 |

4-4（6 patch）、4-5（6 patch）、4-8（5+1 patch）是重灾区。Review 成为质量的主要安全网，但依赖 review 补救不是可持续模式。

## 5. Key Learnings

1. **编译验证是底线**。4-8 的编译错误表明"实现后未运行 cargo test 就标记 done"的情况确实发生。验证命令必须在标记 done 前执行并记录结果。
2. **Review 密度上升反映 story 复杂度上升**。Epic 4 的全栈 story（4-4/4-5）和后端复杂 story（4-8）出错面远大于 Epic 3。需要在实现阶段加强自检，而非依赖 review。
3. **UTC/本地日期是反复出现的陷阱**。需要在时间相关代码中建立统一模式并强制 review 检查。
4. **文档同步行动项未被执行**。Epic 3 建立了文档同步要求，但 4/8 stories 的 Dev Agent Record 为空。需要将文档完成纳入 done definition 的强制检查。
5. **前端 flaky 测试是慢性债务**。贯穿整个 Epic 未修复，每次都在 Dev Notes 中"与本 story 无关"地跳过。需要专项处理。

## 9. Significant Discoveries

1. **4-8 编译失败**暴露了验证流程的缺口 — 这不是单纯的代码错误，而是流程问题：实现后未运行验证命令就标记 done。需要流程级修复。
