## 2. What Went Well

### 2.1 Agent Runtime 边界成型

Epic 2 建立了 `sidecar.rs`、`agent_bridge.rs`、AgentBridge、SSE 映射、fallback 机制，使 opencode 成为 EgoSync 的本地 agent runtime，而不是简单外部 API。

正面影响：后续角色委派、工具调用、Skill、MCP、任务自动化都能建立在同一 runtime 边界上。

### 2.2 架构纠偏及时

`2-0d-opencode-custom-tools-replace-mcp.md` 是 Epic 2 的关键突破。团队识别到内部 MCP host 受 opencode project instance / InstanceState 绑定影响，导致 MCP 连接成功但 LLM tools 列表缺少 EgoSync 自有工具。最终改为 opencode Custom Tools + bus event 监听 + bridge 模式。

正面影响：避免继续扩大不稳定内部 MCP host 路线，为后续任务工具、角色涌现、委派、Skill/MCP 能力管理提供默认路径。

### 2.3 角色协作闭环形成

Epic 2 交付了角色 CRUD、角色视图、角色个性化语调、管家意图路由、角色涌现建议、delegate bridge。角色系统从“能切换聊天”推进到“管家可组织角色协作”。

正面影响：产品体验从静态角色列表升级为多角色协同系统。

### 2.4 记忆可信度闭环形成

`2-6` 到 `2-9` 形成了结构化记忆闭环：提炼、查看、来源溯源、选择性遗忘、防回流、透明引用、不确定性表达。

正面影响：记忆不再只是后台事实库，而成为用户可审阅、可删除、可追问依据的可信体验。

### 2.5 能力边界产品化

Skill/MCP 不只是 UI 开关，而是同步影响 prompt、permission、opencode config、runtime 行为。`2-10` 确立了“禁用能力不得在 prompt 中声明，且 runtime 也要硬阻断”的原则。

正面影响：后续外部能力扩展时，系统不容易出现“UI 禁用但 agent 仍可调用”的能力泄漏。

### 2.6 mock 数据债务有效削减

Epic 2 修复了 `AddRoleModal` 仍走 mock、RoleView mock messages、Skill/API key mock UI 等问题。

正面影响：减少“自动化测试通过但真实产品路径断裂”的概率。

## 3. Challenges and Friction

### 3.1 追踪状态不一致

复盘发现四个追踪问题：

1. `epic-2` 复盘前仍是 `in-progress`。
2. `epic-2-retrospective` 复盘前仍是 `optional`。
3. `2-0d-opencode-custom-tools-replace-mcp.md` 是重大架构 story，但未登记在 sprint-status。
4. `2-4`、`2-5` story 文件头仍显示 `review`，但 sprint-status 标记为 `done`。

影响：复盘、审计、后续 story 依赖判断会出现口径分歧。Epic 1 已经提出“文档状态是交付物的一部分”，Epic 2 仍有同类问题。

### 3.2 真实 runtime 验证不均衡

Epic 2 自动化测试数量与质量明显提升，但真实 Tauri + opencode + event + tool 的运行链路验证并不均衡。部分 story 有桌面/UI 验证记录，部分 story 仍留有人工确认或未运行桌面端验证。

影响：Agent 能力路径可能出现“单元测试绿，但真实用户路径仍需确认”的风险。

### 3.3 LLM/tool 协议复杂性反复出现

Epic 2 多次遇到工具调用与流式协议问题：tool 未触发、malformed JSON、SSE 清理、mid-stream error、session cache、MCP scope、fallback 语义等。

影响：后续 Epic 3 的任务工具与自动分类不能被当作普通函数调用，必须按协议矩阵治理。

### 3.4 多 scope 前端状态风险升高

MemoryTab、source loading、role/category 切换、reference target、delete pending、MCP refresh 等路径暴露出 stale state / request race 风险。

影响：Epic 3 会引入 role-scoped tasks、quadrant、status、manual override、classification confidence、filter/query key，状态组合更复杂。

### 3.5 Deferred 归宿仍不够集中

Epic 2 story notes 中仍散落多个 deferred：opencode session / event / scope、`opencode.json` 并发写、Cargo registry override、MCP session cache、archived role 校验、可访问性债务等。

影响：这些不一定阻塞 Epic 3，但如果不归类，会在后续 story 或加固阶段集中返工。

## 4. Key Learnings

1. **任务工具应继承 Custom Tools / bridge 模式。** `2-0d` 已证明内部 MCP host 不是 EgoSync 自有工具的稳定默认路线。
2. **LLM/tool 是协议，不是函数。** 工具成功、不触发、参数缺失、malformed JSON、bridge 失败、fallback、stream cleanup 都需要测试与用户反馈语义。
3. **文档状态仍然是交付物。** sprint-status、story 文件头、Completion Notes、Verification、File List 必须在 story 关闭时一致。
4. **记忆可信度依赖完整链路。** 提炼、来源、删除、防回流、引用、不确定性必须一起设计，否则会损害用户信任。
5. **能力开关是跨层协议。** UI、prompt、permission、opencode config、runtime 必须一致。
6. **真实 runtime 剧本不可替代。** Tauri + opencode + event + tool 的真实路径不能只靠 jsdom 或 service 测试证明。
7. **Epic 3 的任务系统不是普通 CRUD。** 它会连接角色、记忆、工具调用、四象限推理、权限和后续仲裁。

## 8. Significant Discoveries

### 8.1 Epic 3 不是普通 CRUD

Epic 3 的任务系统会同时连接：

- 角色 scope
- 管家全局视图
- opencode AgentBridge
- Custom Tools
- Skill/MCP 权限边界
- 记忆/对话来源
- 四象限分类
- 不确定性与解释链
- 后续主动循环与仲裁

影响：Epic 3 计划方向仍然正确，但 Story 3.1 / 3.3 前必须补协议和边界。

### 8.2 `2-0d` 应被视为架构转折点

`2-0d` 虽未登记在 sprint-status，但它解决了内部 MCP host 路线的不稳定问题，并确定 EgoSync 自有工具优先使用 Custom Tools / bridge / event router。

影响：Epic 3 任务工具应沿用该路径，不应恢复旧 internal MCP host。

### 8.3 手动覆盖分类必须被产品化

Epic 3 自动四象限分类如果无条件覆盖用户手动调整，会破坏用户信任。

影响：用户手动修改 quadrant 后，自动分类不得无条件改回；覆盖规则必须写入 AC 并可解释。
