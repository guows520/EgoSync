## 1. 问题陈述（Issue Summary）

**触发**：非故事触发。产品负责人于 2026-09-17 提出"把当前应用做一个云端 WEB 版"。

**动机**（boss 于 Correct Course 会话中确认）：
1. **随时随地访问**——不受限于自己的电脑，任意浏览器可用，免安装；
2. **多设备数据同步**——多设备访问同一份数据，无需手工搬运。

**已确认的决策参数**（本提案的边界条件）：

| 决策点 | 裁决 |
|---|---|
| 路径 | **B：云端托管完整版**（服务器运行完整引擎+数据，WEB 是其原生 UI） |
| 数据拓扑 | **云脑单源**——引擎+数据只在云端跑一份，所有客户端（WEB/手机/桌面应用）连云端；不做双引擎同步 |
| 托管形态 | **先自托管单用户**（用户自有 VPS/NAS，Docker 部署），多租户 SaaS 后议 |
| 启动时机 | **V1 收尾后启动**（不中断在飞的 Epic 12-14 与 V1 加固） |
| Android 伴侣 | **照常**（Epic 12-14 原计划不变，仍连接桌面引擎） |

**与既有规划的冲突**（显式暴露，非折中调和）：

本次决策**部分取代**以下既有裁决，各条理由与调和方式见 §4.1-P10 决策日志新增条目：

- `prd-egosync.md` §1 Vision："产品采用本地优先架构"——数据主权承诺的表述从"数据存本地"升级为"数据属于用户（本地版存本地 / 云端版存用户自托管服务器）"；
- FR-25 本地优先存储、NFR-1 零云端依赖——按部署形态分别成立（桌面版不变；云端版以自托管保留主权叙事）；
- §6.2 Non-Goal"云端数据同步/托管 V2"——云端托管（自托管单用户）进入产品范围，多租户 SaaS 维持 Non-Goal；
- 决策日志 #17（2026-08-25）对"独立手机 App + 云端托管引擎"的否决——否决语境是**手机伴侣的替代方案**（需第二套引擎 + 双数据源）；本次是**独立部署形态**（云脑单源、无同步层、桌面版保留），语境不同，非原案复活。

**保留的异议记录**：Correct Course 分析中曾推荐路径 A（WEB 伴侣：浏览器作为第三客户端经零知识中继连接桌面引擎，成本约一个 Epic），boss 明确选择路径 B。A 的核心组件（WEB 前端、传输抽象）在 B 中依然复用，本提案的 Epic 16 即其化身；差异在引擎位置（B 在云端，A 在桌面）与产品能力上限（B 解锁 24/7 常驻工作循环）。

### 2.3 技术影响（概要，细节归架构阶段）

1. **引擎无头化**：现有 Rust `services/` 编排层、`db/`、`agent_bridge`、`sidecar` 与 Tauri 耦合点集中在 `commands/`（薄层）——将引擎抽出为独立 server binary（axum）是可行且代价可控的抽取；桌面版继续以 Tauri 壳包裹同一引擎。
2. **传输对等**：前端 `services/*.ts` 目前封装 `invoke()`——引入传输抽象（IPC ⇄ HTTPS/WSS）后，同一 React 应用既在 Tauri 里跑、也在浏览器里跑。协议 schema 本就预留了 TS 类型生成。
3. **密钥管理**：keyring 在服务端不可用——LLM API Key 改为服务端密钥管理（env/加密文件），浏览器永不可见。
4. **opencode on server**：sidecar 生命周期管理模式平移到服务器上下文，`agent_bridge` 协议不变。
5. **产品能力解锁**：FR-10 的"工作循环仅在应用运行时执行"假设在云端版被打破——服务器常驻 = 角色 24/7 思考、晨间简报按时生成。这是 B 路径最实质的产品增量。
6. **主要风险**：引擎抽取对桌面版的回归风险（以传输对等测试 + 现有桌面 E2E 套件兜底）；公网端点安全面（TLS/认证/限流）；浏览器流式（SSE/WS）稳定性。

### 2.4 成本/工期/风险评估

- **工作量**：高——3 个新 Epic（约 11-13 个故事）；但因复用 React UI 与 Rust services，远低于"第二个产品"的从零成本（无 UI 重写、无引擎重写、无 LLM 适配重写）。
- **风险**：中——抽取回归（有测试兜底）、公网安全（自托管单用户缩小攻击面）、浏览器环境差异。
- **时间线**：V1 交付不受影响；云端版赛道预计 V1 收尾后 4-8 周 agent 工作量成形。

## 3. 推荐路径（Recommended Approach）

**采用：Direct Adjustment（新增赛道式直接调整）**——不回滚任何已完成工作、不改动 V1 MVP 范围、不中断在飞史诗；以三个新 Epic（15-17）承载云端版，V1 收尾后启动。

**已评估并否决的备选**：

| 备选 | 否决理由 |
|---|---|
| 路径 A：WEB 伴侣（浏览器连桌面引擎经零知识中继） | 成本更低（约 1 Epic）且不违本地优先，但桌面关机即降级只读，无法满足 24/7 与真同步动机；boss 已知情后选择 B。其可复用部分已吸收进 Epic 16 |
| 路径 B-双脑并行（桌面+云端双引擎+同步层） | 决策 #17 记录的"双数据源深坑"；双引擎同时跑工作循环产生重复建议与冲突；工程量为分布式系统级别 |
| 路径 B-多租户 SaaS | 需账号体系/隔离/计费/合规，运营责任全来；与当前个人产品定位不匹配；boss 裁决"后议" |
| Rollback 类方案 | 无可回滚对象：变更是新增而非纠正 |

**成功的衡量**（建议，供 PM 细化）：云端版部署后——① boss 在任意浏览器完成一次完整管家对话+任务操作；② 桌面版与云端版各自独立可用且互不干扰；③ 服务器重启后数据与配置完整；④ 工作循环在无人访问时段持续产生建议。

### 4.2 架构（architecture.md）

**A1 [交由深化] 新增增量章节"云端托管版（Cloud Edition）"**，必须覆盖以下决策域（架构师 Winston 深化，增量章节范式与手机伴侣章节一致）：

1. **引擎无头化抽取**：`services/`、`db/`、`agent_bridge/`、`sidecar/` 与 Tauri 解耦（耦合点集中在 `commands/` 薄层与 `lib.rs` 注册）；抽出 engine crate/library；桌面 Tauri 壳与 server binary 共用同一引擎。回归兜底=桌面 E2E 套件全绿。
2. **server binary**：axum，暴露与 Tauri command 一一对应的 HTTPS/WSS API + SSE 事件流（`llm:stream` 等事件语义平移）；认证中间件（单用户令牌）；限流；TLS 终结（内置或反代）。
3. **传输对等**：前端 `services/*.ts` 引入传输接口（`invoke()` ⇄ HTTP/WSS 客户端）；React 应用双目标构建（Tauri / browser）；流式事件双承载（Tauri Event ⇄ SSE/WS）。
4. **密钥管理**：服务端 secret store（env/加密文件）承载 LLM API Key；keyring 仅桌面版使用。
5. **opencode 服务端化**：sidecar 生命周期管理平移；opencode 二进制进 server 镜像。
6. **数据与备份**：双 SQLite 库挂服务器卷；复用既有数据导出/导入机制作为备份/恢复路径（数据主权闭环）。
7. **部署**：docker compose（server + opencode + 静态 WEB）；healthz；结构化日志。
8. **安全威胁模型**：公网端点、CORS/CSP、浏览器端不落敏感数据、快照/会话缓存的浏览器存储策略。
9. **工作循环常驻化**：FR-47 的调度语义（服务器时区、简报时间语义）。

**必须显式回答的开放问题**（交架构阶段裁决）：多端并发会话语义（同一账号多浏览器同时在线）；桌面客户端远程模式（FR-48）的连接/切换状态机；与中继/伴侣协议的远期收敛（Android 直连云端实例是否作为后续形态）。
